# CRSF2: маршрутизация двух LAN через AmneziaWG

Docker-шлюз для VDS соединяет роутер/шлюз сети Radio `192.168.66.0/24` и роутер/шлюз сети Module `192.168.55.0/24`. ESP32 остаются обычными LAN-устройствами: VPN-клиент запускается на роутере или отдельном Linux-шлюзе, а не на платах.

Настройки CRSF2 из [технического задания](./inintial/tech_task.pdf) менять не нужно: Module остаётся мастером с постоянным IP `192.168.55.11`, Radio подключается к этому адресу, обмен идёт по UDP `7777`. Внутренний трафик между LAN маршрутизируется без SNAT/masquerade. На VDS открыт только внешний UDP-порт VPN; пробрасывать UDP `7777` из интернета не требуется.

## Схема адресов

| Узел | VPN-адрес | Локальная сеть | Удалённая сеть |
|---|---:|---|---|
| VDS / AmneziaWG | `10.77.0.1/24` | — | обе |
| Шлюз Radio | `10.77.0.2/32` | `192.168.66.0/24` | `192.168.55.0/24` |
| Шлюз Module | `10.77.0.3/32` | `192.168.55.0/24` | `192.168.66.0/24` |

Если подсети или VPN-адреса уже используются, выберите непересекающиеся адреса и согласованно поменяйте их в Compose, конфигурациях peers и маршрутах роутеров. Пример предполагает, что VDS работает под Linux и Docker Engine поддерживает `network_mode: host` и `/dev/net/tun`.

## 1. Подготовьте VDS

Установите Docker Engine и Docker Compose plugin на Linux VDS. В облачном firewall и на хосте разрешите входящий **UDP `51820`**. Не открывайте `7777` в интернет.

Включите IPv4 forwarding на хосте:

```sh
sudo install -m 0644 /dev/stdin /etc/sysctl.d/99-crsf2-routing.conf <<'EOF'
net.ipv4.ip_forward=1
EOF
sudo sysctl --system
```

Для временного включения до перезапуска можно выполнить `sudo sysctl -w net.ipv4.ip_forward=1`. Контейнер откажется запускаться, если forwarding выключен.

## 2. Создайте ключи и конфигурацию сервера

Ключи для этого рабочего набора уже сгенерированы. Чтобы создать новый набор, сначала соберите образ и используйте инструменты из него:

```sh
docker compose build
docker run --rm --entrypoint awg crsf2-amneziawg:local genkey
```

Для сервера и каждого peer сгенерируйте отдельный приватный ключ; для каждого вычислите публичный:

```sh
printf '%s\n' 'ПРИВАТНЫЙ_КЛЮЧ' | docker run --rm -i --entrypoint awg crsf2-amneziawg:local pubkey
```

Храните приватные ключи только на соответствующих шлюзах. Не отправляйте их в чат и не добавляйте в систему контроля версий.

В рабочем каталоге уже созданы `config/server.conf`, `config/radio-peer.conf` и `config/module-peer.conf` с отдельными ключами сервера и обоих peers. Эти файлы исключены из Git, так как содержат приватные ключи. Храните их безопасно и не отправляйте приватные ключи в чат.

В клиентских файлах перед импортом укажите публичный IP или DNS VDS в `Endpoint` (UDP `51820`). Параметры AmneziaWG `Jc/Jmin/Jmax`, `S1/S2`, `H1-H4` уже согласованы с сервером. Если создаёте новый набор ключей, используйте шаблоны `.example` и замените все `CHANGE_ME_...`; значения параметров AmneziaWG должны совпадать на обеих сторонах.

## 3. Запустите шлюз на VDS

Перед запуском проверьте, что файл `config/server.conf` создан и не содержит шаблонных ключей:

```sh
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 amneziawg
```

Контейнер создаёт userspace-интерфейс `awg0`, включает адрес `10.77.0.1/24` и маршруты к обеим удалённым LAN. В Compose используется host networking: секция `ports` намеренно отсутствует.

Проверка на VDS:

```sh
sudo docker exec crsf2-amneziawg awg show awg0
ip route get 192.168.66.73
ip route get 192.168.55.11
```

В выводе `awg show` после подключения должны обновляться handshake и счётчики передачи.

## 4. Настройте два роутера/шлюза

Скопируйте `config/radio-peer.conf` и `config/module-peer.conf` на соответствующие роутеры или отдельные шлюзы, укажите в каждом публичный IP или DNS VDS в `Endpoint`, затем импортируйте профиль как **AmneziaWG**. Обычный WireGuard-клиент может не поддерживать параметры AmneziaWG. Не передавайте конфиг одного peer другому: в каждом находится приватный ключ соответствующего peer.

- Radio peer: приватный ключ Radio, публичный ключ VDS; `AllowedIPs` содержит VPN-подсеть и LAN Module `192.168.55.0/24`.
- Module peer: приватный ключ Module, публичный ключ VDS; `AllowedIPs` содержит VPN-подсеть и LAN Radio `192.168.66.0/24`.
- Настройте на обоих peer автоподключение. `PersistentKeepalive = 25` помогает шлюзам за NAT поддерживать исходящий туннель к VDS.

Если VPN-клиент установлен на основном LAN-роутере, добавьте удалённую LAN через VPN-интерфейс согласно интерфейсу его прошивки. Если шлюз VPN — отдельное устройство в LAN, добавьте на основном роутере статический маршрут:

| Где | Сеть назначения | Следующий хоп |
|---|---|---|
| Роутер Radio | `192.168.55.0/24` | LAN-IP шлюза Radio |
| Роутер Module | `192.168.66.0/24` | LAN-IP шлюза Module |

На обоих роутерах разрешите пересылку трафика между LAN и VPN. Если их firewall по умолчанию блокирует forwarding, добавьте правила для UDP `7777` между платами (пример: `192.168.66.73:7777` ↔ `192.168.55.11:7777`) и для ICMP при необходимости диагностики. Не подменяйте адреса между LAN: не включайте masquerade/SNAT для трафика `192.168.66.0/24` ↔ `192.168.55.0/24`.

На VDS firewall также должен пропускать пересылку между VPN peers в обоих направлениях. Для хостов с iptables пример правил (добавьте их в используемый постоянный firewall, до блокирующих правил):

```sh
sudo iptables -I FORWARD 1 -i awg0 -o awg0 -s 192.168.66.0/24 -d 192.168.55.0/24 -j ACCEPT
sudo iptables -I FORWARD 1 -i awg0 -o awg0 -s 192.168.55.0/24 -d 192.168.66.0/24 -j ACCEPT
```

Адаптируйте эти правила, если на VDS используется nftables или другой firewall, и сохраните их штатным для дистрибутива способом. Не добавляйте для этих LAN правила NAT/masquerade. Ограничьте входящий UDP `51820` адресами peer, если их публичные адреса постоянны.

## 5. Проверьте CRSF2

1. Проверьте VPN handshake и двусторонний рост счётчиков на `awg show awg0`.
2. С компьютера в сети Radio проверьте доступность Module: `ping -n 20 192.168.55.11` в Windows или `ping -c 20 192.168.55.11` в Linux. Ping проверяет ICMP, а не UDP и не сессию CRSF2.
3. Проверьте firewall, маршруты туда и обратно, а также отсутствие NAT между LAN.
4. Откройте Serial Monitor обеих плат на `115200` бод. Подтверждение — установленная сессия CRSF2, `NET ONLINE`, растущие сетевые `tx`/`rx` и чтение параметров Nomad. Для устойчивости наблюдайте несколько минут; целевой RTT по требованиям — менее `250 мс`.

UDP `7777` работает только как трафик между подсетями через туннель. `Test-NetConnection -Port 7777` проверяет TCP и не является проверкой CRSF2/UDP.

## Эксплуатация

```sh
docker compose logs -f amneziawg
docker compose restart amneziawg
docker compose down
```

При смене адреса Module обновите статический IP платы, адрес мастера в настройках Radio, peer AllowedIPs и маршруты. При DHCP-адресе Radio настройте резервирование или разрешите соответствующий диапазон в firewall.

Подробнее о поведении текущих плат — в [requirements.md](./inintial/requirements.md) и [tech_task.pdf](./inintial/tech_task.pdf). Сетевые значения в примерах взяты из этих материалов и должны быть сверены с фактической адресацией.
